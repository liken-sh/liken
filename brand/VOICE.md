# Voice

These rules govern every word published on liken.sh and its
subdomain sites: page copy, guides, reference text, and the field
descriptions that generators turn into pages. Read them before you
write. Scan your text against them before you publish. This file
follows its own rules and stands as an example of them.

The base standard is Simplified Technical English (ASD-STE100). The
rules below are the ones that matter most on these sites.

## Words

- Use simple words that most readers know.
- Use one word for one thing, every time. Do not vary a word for
  variety.
- Use short words. Write "use", not "utilize" or "leverage". Write
  "start", not "commence".
- Do not use slang, idiom, or metaphor.
- Do not write "best practices", "comprehensive", "robust",
  "seamless", or "root cause".
- Write `liken` in the code face everywhere it appears, because it
  names the code.
- Show a technical name exactly as it is. Put commands and file
  names in inline code, and code in code blocks.

## Sentences

- Use the active voice. Write "the installer writes the disk", not
  "the disk is written by the installer".
- Use the imperative form for instructions. Write "Run the command."
- Put one instruction in each sentence, and one topic in each
  sentence.
- Keep an instruction to 20 words or fewer. Keep a descriptive
  sentence to 25 words or fewer.
- If a condition applies, start the sentence with it. Write "If the
  boot fails, read the report."
- Use only the simple tenses. Do not use the "-ing" form of a verb
  when another form works.
- Do not turn a verb into a noun. Write "install the release", not
  "do the installation of the release".
- Do not use an em-dash. Use a period or a comma.
- Do not compress a sentence until it is dense. If a reader must
  read it twice, rewrite it with plainer words.

## Software is a machine

- Software has no mind. A program reads, writes, starts, refuses,
  and fails. Do not write that it wants, knows, thinks, tries,
  decides, learns, or believes.
- Software has no body. Do not write that code sits on, stands on,
  reaches into, or rides on anything.

## Claims

- State facts that a reader can check. Put the value next to the
  limit that gives it meaning, and the before next to the after.
- Say plainly which parts come from upstream projects and which
  parts this project adds. Do not claim more than the code does.
- Delete a sentence whose only job is to sound good: a slogan, an
  aphorism, or a closing flourish.
- End a section on its last fact, not on a summary of the section.

## Structure

- Give the answer first. Then give the data that supports it.
- Put one topic in each paragraph, and start the paragraph with its
  topic sentence. Keep a paragraph to six sentences or fewer.
- Name the subject in a heading. Write "The release channel", not
  "What about releases?" or "Getting your bits".
- Use a vertical list for steps, in the order a reader performs
  them.
- Put a warning before the step it applies to, and make it a
  command. Write "Do not unplug the machine during this step."
- Tell the reader the result of an action when the result is not
  obvious.
