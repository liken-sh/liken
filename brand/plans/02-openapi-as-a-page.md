# 02, The OpenAPI document as a page

Every manual whose operator serves an HTTP API gets one generated
reference page, `Routes`, rendered from that API's OpenAPI 3.1
document by one generator this repository publishes. The page is
Markdown that the shared theme renders. There is no Swagger UI and
no JavaScript.

## The problem

The display, audio, and media operators each serve a capture API,
and each API renders its own OpenAPI document from its router, so
the document cannot miss a route the program answers. Each manual
then has a hand-written page that tells the story of the API: how it
negotiates a format, how it reads a time span, who may capture, and
what each error means. What no page holds is the list: the routes,
their parameters, the statuses each one answers, and the fields each
answer carries. That list is in the document, which a reader reaches
today as raw JSON.

A rendered viewer was the first idea. Swagger UI and Redoc are
JavaScript bundles that would arrive on three static sites, carry
their own look, and break the link check, which resolves a link
against the headings a page renders. A generated page costs one
program and keeps the sites as they are.

## The design

```
openapi.json                          the API's own document
        |  go tool apiref             this repository's generator
        v
content/docs/reference/routes.md      generated by make, beside api.md
```

### The generator

`apiref/` is a Go program, run as `go tool apiref` and pinned in each
docs module the way `crdref` is:

    go tool apiref -title Routes -weight 55 \
      -postamble apiref/routes-postamble.md \
      openapi.json content/docs/reference/routes.md apiref/routes-preamble.md

It takes the same flags and the same three positional arguments as
`crdref`, because the two run from the same kind of Makefile rule.

The page opens with the hand-written preamble, then the document's
own title, version, summary, and description. Then it gives one
section for each operation, headed with the method and the path, as
in `## GET /v1/display/displays/{name}/screen.png`. A section is one
method on one path, and not one path, because the parameters and the
answers of a `GET` are not those of an `OPTIONS` on the same path.
Each section holds the summary, the description, and up to five
tables: the parameters, the request body, the answers, the header
fields those answers carry, and the link relations they declare. A
bold line names each table, because four tables under one heading
otherwise read as one table with four header rows. A table appears
only when the operation has that part, and its line appears with it.
A document whose answers declare no content, because every body is a
live capture, gets a two-column answer table instead of four.

Under the sections come the component schemas, rendered as the field
tables `crdref` writes for a CRD: the same four columns, the same
dotted heading for a nested object, and the same id on each row. A
response that names a schema links to that schema's section. Last
come the security schemes and the requirement over every route, then
the hand-written postamble.

Every link the page writes lands on a heading or a row of the same
page, and both ends come from `linkcheck.Anchor`, which holds the one
implementation of Hugo's id algorithm. A test renders the display
manual's own document and resolves every link on the result.

The reader follows the document's order and not Go's map order, so
the paths, the methods, and the statuses read in the order the
program that wrote the document declared them.

### Each manual

Each repository with an API gets:

* `docs/apiref/routes-preamble.md` and
  `docs/apiref/routes-postamble.md`, hand-written. The preamble says
  what the API is and links the narrative page. The postamble says
  where to fetch the document itself.
* A rule in `docs/Makefile` that names the OpenAPI document the
  repository already has, and the generated page in `GENERATED`, so
  `make build` and `make test` both regenerate it. The three
  repositories hold that document in three places: display generates
  it from the binary, audio commits it under the site's static tree,
  and media commits it at the repository root and embeds it.
* One sentence in the hand-written API page, in its routes section,
  that links the generated page. Nothing else about that page
  changes.

The generated page's weight puts it directly after the API page in
the reference section.

### How it is proved

`make test` in this repository runs the generator's tests: a golden
page from a small document that holds every shape (an operation with
no parameters, a path parameter an operation overrides, several media
types under one status, an enum, a reference chain, a request body,
response headers, a link relation, a nested object, a map, a type
that may be null, and a pipe that must be escaped), and the
display manual's real document for the whole-page checks.

In each manual, `make -C docs build` builds the site with the page in
it, and `make test-docs` runs the link check against the freshly
generated page.

## Open problems

* **The `servers` member is not on the page.** Two of the three
  documents carry a placeholder origin, which the served copy
  replaces with the origin the request reached, so printing it would
  print a name no caller uses. The preamble says where the API is.
* **A `HEAD` section repeats its `GET` section.** The documents
  describe the two operations separately, with the same parameters
  and the same statuses, so the page writes both. Folding them would
  mean the page deciding that two operations are one.
* **The title is set in the code face.** It is `display-api` and
  `media-api` in two documents, which are program names, and a
  sentence in the third. That one reads oddly in a code face.
* **What no document uses is not rendered:** `callbacks`,
  `webhooks`, `examples`, `oneOf`, `anyOf`, `allOf`, and a `servers`
  entry on one operation. A document that uses one of these renders
  a page that does not mention it.
